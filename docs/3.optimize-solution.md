# Solution Optimization

## 1. Algorithm Optimization

### Limitations of the Initial Approach

The naive approach started with guessing `"crane"` and filtering candidates sequentially. However, simply choosing the next candidate in arbitrary order failed to maximize information gain per guess. Choosing low-entropy words led to redundant guesses and higher average attempt counts.

### Optimized Heuristic (Information Gain & Positional Letter Frequency)

- **Strategic Starting Words**: Precomputed high-entropy starting words mapped to each word length (lengths 2–15), maximizing early vowel and common consonant coverage (e.g., `crane` for 5 letters, `roam` for 4 letters, `stare` / `soare` variations).
- **Strict Feedback Pruning (`matches_feedback`)**: Accurate handling of duplicate letters, tracking exact occurrences when letters appear in both `present`/`correct` and `absent` feedback.
- **Weighted Letter Frequency Scoring**:
  - Scores candidate words based on English letter frequency weights (`E, T, A, O, I, N, S, R, H, D, L, U, C, M...`) across distinct letters.
  - Prioritizes words containing unseen common letters during early steps to prune maximum possible candidates simultaneously.
  - Achieves puzzle resolution in an average of 3–5 attempts.

## 2. User Interface & Experience (UI/UX) Optimization

### Initial UI Limitations

- Plain unstyled HTML without visual hierarchy.
- No client-side input validation for secret words.
- Single-column vertical stacking requiring continuous page scrolling.
- No seamless mechanism to switch between Local test simulation and Live remote environments.

### Optimized UI/UX Implementation

- **3-Panel Dashboard Layout**: Fits all visual elements and controls within a single viewport without requiring scrolling.
  - **Left Panel (Control Panel)**:
    - API Environment Switch (Local Evaluator vs. Live Votee API).
    - Mode Selection: Daily, Random, Selected.
    - Word Length selector pills (lengths 3–8).
    - Random Seed manager & sample word generator.
    - Secret word input field for Selected mode.
    - Start Solver & Reset buttons.
  - **Center Panel (Live Guessing Board)**:
    - Interactive Wordle board grid with 3D tile-flip animations.
    - Real-time step counter & color legend (Correct, Present, Absent).
  - **Right Panel (Results & Analytics)**:
    - Victory summary & time execution metrics.
    - Search Space Reduction bar chart tracking candidate shrinkage.
    - A-Z Analyzed Letter Matrix.
    - Step-by-step audit history.
- **Micro-animations & Glassmorphism**: Clean modern aesthetics with CSS variables, smooth transitions, and feedback badges.
- **Real-time Input Validation**: Instant client-side feedback for length and character constraints.

## 3. Performance & Architecture Optimization

### Initial Performance Bottlenecks

- Monolithic batch solving endpoint forced the client to wait until full completion, preventing real-time visualization and step-by-step inspection.
- Large dictionary JSON file (~6.8MB) required loading all words into memory at once.

### Performance Improvements

- **Step-by-Step Interactive Solver (`/solver/next-guess`)**: Allows live interactive visualization with fine-grained step control and debugging.
- **Dictionary Pre-processing & Length Chunking**: Segmented the dictionary by word length (`words_len_*.json`), reducing RAM footprint and search complexity to $O(K)$ where $K$ is the word count for that specific length.

## 4. Docker Image Optimization

### Initial Dockerfile Limitations

- Monolithic image size (~220MB).
- Ran under root privileges.
- Lacked separated development vs production build stages.

### Multi-Stage Build & Security Enhancements

- **Multi-Stage Builds**: Utilized Python virtual environment copies and Alpine-based Nginx servers, substantially reducing final image sizes.
- **Native Python Healthcheck**: Eliminated external utility dependencies like `curl`.
- **Non-Root Execution**: Runs under designated unprivileged users (`appuser` / `nginx`) for security compliance.
- **Target Stages**: Distinct `development` (with hot reloading) and `production` targets in Dockerfile.
