# Problem Resolution

## Problem 1: Understanding Wordle Mechanics & Dictionary Preparation

To establish the foundation, we analyzed the standard Wordle rules and prepared an English word dictionary at [this link](https://wordlegame.org). The dictionary dataset is utilized for:

- Serving as the pool of valid candidate guesses.
- Selecting optimal starting words across different word lengths.
- Testing and benchmarking algorithm performance.

The English word list was sourced from the open-source repository at (this link)[https://github.com/dwyl/english-words].

### Dataset Evaluation

- Formatted as clean, lowercase English words.
- Segmented by word length to ensure fast indexing and low memory usage.

## Problem 2: Local Mock API for Independent Development & Testing

To enable fast, isolated local development without depending on or impacting live external servers, a local mock evaluator API was developed with matching endpoints:

- `/api/v1/daily`: Evaluates guesses against the deterministic daily word.
- `/api/v1/random`: Evaluates guesses against a random word (seed-supported).
- `/api/v1/word/{word}`: Evaluates guesses against an arbitrary target word.

The local evaluator supports a `TEST_MODE` configuration flag in `.env`. When active, it includes diagnostic headers and deterministic behavior for automated regression testing.

## Problem 3: Core Solver Algorithm Implementation

### 1. Algorithm Details

- **Strategic Starting Word**: Defaults to `crane` for 5-letter words (or highest-frequency precomputed starting words for lengths 2–15).
- **Candidate Filtering (`matches_feedback`)**:
  - `correct`: Keep candidates with the exact letter at the specified slot.
  - `present`: Keep candidates containing the letter, but exclude those with the letter at the current slot.
  - `absent`: Eliminate the letter from consideration unless it also appears as `present`/`correct` elsewhere in the guess (strict frequency bounds).
  - Iterate feedback filtering until the search space converges.

```pseudocode
current_guess = "CRANE" // Strategic starting word

result = HTTP_GET(https://wordle.votee.dev:8000/daily?guess={{current_guess}})

while CheckResult(result) is not all_correct:
    filter_candidates_by_feedback(result)
    current_guess = select_optimal_next_guess(remaining_candidates)
    result = HTTP_GET(https://wordle.votee.dev:8000/daily?guess={{current_guess}})

print("Solved:", current_guess)
```

## Problem 4: Visualizing the Guessing Process

### 1. User Interface Design

The visualizer is built using basic HTML just show a button "Resolve" and the word-guessing section.

### 2. User Interactions & Live Stepping

- Default mode is Daily (5 letters).
- When the user starts the solver, the frontend coordinates step-by-step API calls (`/solver/next-guess` + evaluation endpoint), rendering live tile flips and updating analytics incrementally.
- Reset restores clean state ready for new sessions.

## Problem 5: Product Packaging & Deployment

- Multi-stage Docker setup for both frontend (Nginx Alpine) and backend (Python 3.11 slim).
- Full stack orchestratable via a single command: `docker compose up --build`.
- Clear instructions and API references documented in `README.md`.
